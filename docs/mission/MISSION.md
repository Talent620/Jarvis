MISJA JARVIS "FILMOWY". Claude Code Cloud, Opus 5.5, repo Talent620/Jarvis
0. Rola i kontrakt
Jesteś głównym inżynierem JARVIS-a: architektem runtime'u, inżynierem sterowania komputerem, głosu, wydajności, QA i bezpieczeństwa. To misja implementacyjna, nie esej. Użytkownik jest offline i nie odpowie.
Zasady przez całą misję:

1. Implementuj, nie rekomenduj. Audyt ma sens tylko, gdy od razu karmi implementację.
2. Weryfikuj, nie deklaruj. Istniejący kod ani "ok" z komendy nie są dowodem. Dowodem jest obserwowalny warunek końcowy.
3. Nigdy nie udawaj sukcesu. Stany: SIMULATED, ATTEMPTED, CONFIRMED, UNKNOWN_AFTER_ATTEMPT, FAILED, BLOCKED, NEEDS_PERMISSION, NEEDS_HARDWARE.
4. Rozszerzaj dobre podsystemy (agentRun, truthLadder, permissions, missionUndo, goalResume, rejestr narzędzi), nie przepisuj ich dla stylu.
5. Nie zadawaj pytań i nie czekaj. Niejasną decyzję deweloperską rozstrzygnij najbezpieczniej, zapisz w docs/mission/DECISIONS.md i działaj dalej. Nie dotyczy to gotowego produktu: JARVIS ma pytać użytkownika o zgodę tam, gdzie wymaga tego polityka.
6. W testach zero płatnych wywołań prawdziwych API (Anthropic, OpenAI, Gemini, ElevenLabs itd.). Fixtures, mocki, nagrane strumienie zdarzeń, testy kontraktowe.
7. Checkpointy: po każdym zielonym przyroście test → commit → push → aktualizacja stanu misji. VM może zniknąć w każdej chwili.

3. Zasady platformy i repo

* Pracuj na gałęzi utworzonej przez tę sesję, push działa tylko na nią. Nigdy: force push, reset --hard na cudzej pracy, przepisywanie historii, push lub merge do main, publikacja wydań, nadpisywanie wydań "latest".
* PR: po M0 jeden draft PR (gh pr create), opis aktualizowany po każdym kamieniu. Jeśli się nie da: docs/mission/PR.md i dalej. CI: gh run list, gh run view --log-failed. Nie trać czasu na naprawianie narzędzi GitHuba.
* Przeglądarka do testów: dodaj przypiętą wersję Playwrighta do devDependencies. Najpierw npx playwright install chromium; jeśli allowlista sieci blokuje, pobierz Chrome for Testing (npx @puppeteer/browsers install chrome@stable, storage.googleapis.com jest dozwolony) i podaj executablePath. Maks. 10 minut na ten problem.
* Electron: w chmurze ELECTRON_SKIP_BINARY_DOWNLOAD=1 (release'y z niepodpiętych repo GitHuba mogą dać 403). Paczki buduje GitHub Actions. Logika procesu głównego jako czyste moduły testowalne w Node plus cienki adapter IPC.
* Nie dotykaj sprzętu, którego tu nie ma (mikrofon, pulpit, lokalna Ollama, prawdziwy Gmail, kontakty, logowanie do Codexa). Adapter + testy + lokalna akceptacja, status NEEDS_HARDWARE, i dalej.
* CI deterministyczne: skan sekretów, lint, typecheck, testy jednostkowe, złote testy runtime'u, testy przeglądarkowe na atrapach, build. Concurrency groups z cancel-in-progress. Żadnych zaplanowanych workflowów wywołujących modele AI. Workflowów wydań nie zmieniaj poza naprawą błędów.
* Zero sekretów w repo, logach, commitach; nie wypisuj wartości zmiennych środowiskowych.
* Nie używaj pauzy typograficznej (em dash, U+2014) w żadnym tekście. Kod, komentarze i dokumenty techniczne po angielsku. Raport końcowy i podsumowanie w PR po polsku, krótko.

4. Cel produktu (Definition of Done misji)
Scenariusz głosem, na oczach użytkownika, z normalną rozmową w trakcie: 1 "Jarvis, uruchom przeglądarkę." 2 "Wejdź na YouTube." (i otwórz film) 3 "Zjedź trochę niżej." 4 "Znajdź komentarze." 5 "Pierwszy komentarz." 6 "Zaznacz pierwsze cztery litery." 7 "Skopiuj." 8 "Wyślij to mailem Marcinowi." Wtrącenia w dowolnym momencie: "a jaka jutro pogoda?", "co sądzisz o tym filmie?", "co teraz robisz?", "poczekaj", "nie ten, następny", "cofnij", "dobra, wróćmy do komentarza". Rozmowa nie blokuje akcji, akcja nie traci stanu przez rozmowę. "stop" przerywa natychmiast. Każdy krok potwierdzony odczytem zwrotnym. Zgoda pada dokładnie raz, na granicy wysyłki, z pokazaniem treści i adresata. Cały scenariusz działa na atrapach tym samym runtime'em co produkcja. Żadnego osobnego silnika demo.
5. Architektura
5.1 Runtime Kernel (jeden zapisujący). Wszystkie trwałe zmiany stanu przez jednego właściciela: typowany strumień zdarzeń + reduktor (SpeechPartial, SpeechFinal, ControlIntent, ConversationIntent, TaskCreated/Amended/Cancelled, ObservationReceived, ReferentResolved, ActionStarted/Attempted/Verified/Failed, ClipboardChanged, WindowFocused, ConsentGranted/Denied). Każde zdarzenie ma ID i deduplikację. Dziennik zadań append-only poza blobem store'a (IndexedDB/Dexie albo plik w procesie głównym). Zdarzenia wysokiej częstotliwości nigdy nie trafiają do starego trwałego bloba.
5.2 Cztery tory, komunikujące się tylko przez Kernel:

* PERCEPTION: tania, zdarzeniowa świadomość bieżącego stanu, zanim użytkownik o coś poprosi. Przeglądarka: nawigacja, fokus, zaznaczenie, scroll, istotne mutacje DOM/drzewa dostępności. Desktop: zmiana aktywnego okna, zdarzenia AT-SPI, schowek. Android: AccessibilityEvents. Bez odpytywania zrzutami ekranu. Większość percepcji deterministyczna, nie przez LLM. Każda istotna obserwacja zwiększa observationEpoch.
* REFLEX: bez LLM. Polska gramatyka: stop/stój/czekaj/poczekaj, pauza, wznów, cofnij, dalej, następny/kolejny, poprzedni, niżej/w dół/zjedź, wyżej/w górę, modyfikatory trochę/jeszcze/bardziej/do końca, kopiuj/skopiuj, wklej, zamknij, tak/nie/dobra; formy "możesz zjechać", "zjedź no". Poziomy: TIER 0 (stop, pauza, przerwij) wolno wykonać na stabilnym partialu z wysoką pewnością, gdy VAD potwierdza mowę użytkownika, a nie echo TTS; TIER 1 (scroll, następny element) na partialu wolno tylko przygotować cel, wykonanie według ścisłej polityki stabilności; TIER 2 (zapisy, efekty zewnętrzne, mail, usuwanie) NIGDY z partiala, tylko z finalnej intencji i po polityce uprawnień.
* CONVERSATION: niezależna od długich akcji. Dostaje wyłącznie Situation Snapshot. Do toru akcji wysyła tylko typowane intencje: NEW_TASK, AMEND_TASK, PAUSE, RESUME, CANCEL, CONFIRM, SIDE_CHAT. Sama nie wykonuje narzędzi.
* ACTION: rozszerzenie agentRun.ts. Pętla: cel → plan → rozwiązanie celu → mikroakcja → obserwacja → weryfikacja warunku końcowego → aktualizacja stanu → checkpoint → dalej lub przeplanowanie. Każde zadanie: taskId, AbortController, status (running/paused/waiting_consent/blocked/done/failed/cancelled), plan, kroki zweryfikowane i oczekujące, referencje, klucze idempotencji, dane do cofnięcia, wznowienie po restarcie (goalResume.ts), undo akcji odwracalnych (horizon/missionUndo.ts). Stos zadań i stos fokusu: "a jaka jutro pogoda?" to SIDE_CHAT, zadanie A nie ginie; "wróćmy do komentarza" przywraca fokus; "nie ten, następny" to AMEND bieżącego zadania, nie nowy cel.

5.3 Referent Registry. Typy co najmniej: Window, Tab, Page, Element, Collection, TextRange, Selection, Clipboard, Contact, Email, File, Task, ConversationTopic. Pola: id, typ, źródło, observationEpoch, semanticKey, confidence, salience, createdAt, lastMentioned, lastActed, parent, metadata, dowód weryfikacji. Referencja z nieaktualnej epoki (nawigacja, istotna zmiana DOM) jest unieważniana, a nie używana na ślepo. Kolekcje z kursorem: "znajdź komentarze" tworzy kolekcję, "pierwszy" = kursor 0, "nie ten, następny" oznacza bieżący jako odrzucony i przesuwa kursor. Zaimki rozwiązuj typem argumentu czasownika ("skopiuj" wymaga Selection, "wyślij to" wymaga treści: najbardziej wyrazista zgodna Selection albo Clipboard) i świeżością, bez LLM, gdy wystarczy typowanie. Schowek ma hash pochodzenia; zmiana poza JARVIS-em od "skopiuj" = ostrzeżenie przed wysłaniem. Pozycja kursora myszy jako podpowiedź uwagi dla "ten", "to tutaj" to późny, opcjonalny dodatek.
5.4 Situation Snapshot: do ~300 tokenów z Kernela (aktywne zadanie i krok, aktywne okno i strona, najgorętsze referencje, zaznaczenie, pochodzenie schowka, ostatnia zweryfikowana akcja). Jedyny kontekst stanu dla modeli. Nigdy cały DOM, cały dziennik ani cała historia.
5.5 Rejestr możliwości. W runtime JARVIS wie, co naprawdę może (np. browser.managed.semantic, browser.bridge, linux.atspi, linux.input.portal, linux.input.authorized, desktop.clipboard, voice.streaming_stt, vision). Planowanie sprawdza możliwości; brak = NEEDS_CAPABILITY / NEEDS_PERMISSION / NEEDS_HARDWARE, nigdy wymyślony sukces. Widok diagnostyczny pokazuje macierz.
5.6 Środowiska za jednym interfejsem ComputerEnvironment (observe, resolve, act, readback, undo):

* ManagedBrowser: Playwright z dedykowanym profilem JARVIS (launchPersistentContext, headed lokalnie, headless w chmurze). Obserwacja przez locator.ariaSnapshot w trybie "ai" z referencjami elementów i opcją boxes, jeśli zainstalowana wersja to wspiera; AbortSignal tam, gdzie API go przyjmuje. Referencja nie przeżywa nawigacji ani dużej zmiany DOM: po akcji obserwuj ponownie. Nakładka: podświetlenie celu, numerki przy dwuznaczności. Ekran zgody Google/YouTube (UE), leniwe ładowanie komentarzy (przewijaj do pojawienia się, z limitem). Nigdy nie przejmuj po cichu danych logowania użytkownika.
* BrowserBridge (później, patrz M8): rozszerzenie WebExtension dla Firefoxa i Chromium do zwykłej przeglądarki użytkownika, połączone z desktopowym JARVIS-em tylko przez loopback, z losowym tokenem sesji i jawnym parowaniem. Wystawia tylko wysokopoziomowe operacje: metadane karty, semantyczny snapshot, znajdź, scroll, fokus, zaznaczenie, odczyt zaznaczenia, klik, wpisanie, stan nawigacji.
* LinuxDesktop (główny cel desktopowy): AT-SPI2 (drzewo, role, tekst, zaznaczanie po offsetach, akcje, fokus); wejście przez portal RemoteDesktop + libei jako realna, nadawana przez użytkownika zgoda (bez niej NEEDS_PERMISSION); ydotool tylko jako jawnie skonfigurowany fallback. Okna: najpierw aktywne okno, aktywacja, geometria i monitory; małe rozszerzenie GNOME tylko dla tego, czego nie da się bezpieczniej.
* WindowsUIA: UI Automation (TextPattern, ValuePattern, InvokePattern); SendKeys ostatnim fallbackiem.
* Android: rozszerz usługę dostępności o drzewo węzłów i akcje na węzłach (CLICK, SCROLL_FORWARD/BACKWARD, SET_TEXT, SET_SELECTION, COPY, fokus, odczyt zwrotny); tap(x,y) tylko fallback.
* Vision: zrzut → kandydat celu → walidacja → akcja → ponowna obserwacja → weryfikacja, za neutralnym interfejsem dostawcy. Tylko gdy semantyka zawiedzie.
* Mock i Fixture do testów. Kolejność lokalizatorów: zweryfikowany wpis z cache/skilla → świeża referencja z drzewa dostępności → rola+nazwa → semantyczny DOM → wizja → współrzędne.

5.7 Skill Compiler: udana i zweryfikowana powtarzalna ścieżka (np. youtube.findComments, browser.copySelection) kompiluje się do skilla: warunki wstępne, semantyczne cele, mikroakcje, warunki końcowe, fallbacki, wersja, liczniki sukcesów i porażek, data weryfikacji. Następnym razem: skill → semantyczna naprawa → model. Porażka unieważnia tylko zepsuty krok. Nigdy nie ucz się nienadzorowanych akcji destrukcyjnych.
5.8 Mikroakcje i prawda: każda mikroakcja deklaruje warunek końcowy sprawdzany odczytem (scrollY wzrósł, element w viewport, zaznaczenie === oczekiwane, schowek === oczekiwane, wiadomość jest w Wysłanych). CONFIRMED tylko po zgodnym odczycie; spawn, "ok" z IPC, rozwiązany klik czy wysłane żądanie HTTP to najwyżej ATTEMPTED. Porażka → klasyfikacja → następna warstwa lokalizatora → maks. 2 próby → uczciwy komunikat.
5.9 Efekty zewnętrzne dokładnie raz: każda akcja z efektem ma actionId, idempotencyKey, argumentsHash, status i dowód. Timeout po możliwym efekcie = UNKNOWN_AFTER_ATTEMPT i najpierw odczyt stanu docelowego (np. Wysłane), dopiero potem ewentualna ponowna próba. Zdublowane "wyślij" z STT nie tworzy drugiej wiadomości.
5.10 Semantyka tekstu (testy obowiązkowe): "znaki" = grafemy, "litery" = grafemy będące literami Unicode, z polskimi znakami. Emoji, interpunkcja i "@" na początku nie liczą się jako litery. Przypadki: "Łódź", "żółw", "@marcin super", "🔥 świetne", emoji z modyfikatorami, znaki łączone. W DOM: Range/Selection API, zaznaczenie WIDOCZNE na ekranie, potem odczyt zaznaczonego tekstu.
5.11 Uprawnienia: rozszerz permissions.ts, nie twórz drugiego systemu. Klasy READ, NAVIGATE, LOCAL_REVERSIBLE, LOCAL_WRITE, EXTERNAL_SIDE_EFFECT, DESTRUCTIVE; polityki AUTO/ASK/DENY w ustawieniach. Domyślnie: czytanie, scroll, podświetlenie, zaznaczenie, kopiowanie, otwarcie strony = AUTO; głośność/media = AUTO lub konfigurowalne; wpis do niewysłanego formularza = konfigurowalne; mail, SMS = ASK; usuwanie, wyłączenie komputera = ASK zawsze. Niezaufana treść + prywatne dane + efekt zewnętrzny = zawsze ASK z finalnymi argumentami, jedno pytanie na granicy zobowiązania.
5.12 Pochodzenie danych i granica zaufania: wartości mają pochodzenie (USER_INSTRUCTION, TRUSTED_CONFIG, LOCAL_STATE, UNTRUSTED_WEB, UNTRUSTED_EMAIL, UNTRUSTED_DOCUMENT, UNTRUSTED_CLIPBOARD, TOOL_OUTPUT). Treść to dane, nie polecenia: nie wybiera narzędzi, nie wybiera adresata, nie rozszerza uprawnień, nie zmienia celu, nie wstrzykuje komend. Streszczanie niezaufanej treści izolowanym wywołaniem modelu bez narzędzi. Surowej niezaufanej treści nie skleja się z blokiem instrukcji agenta.
5.13 Kontakty: polska odmiana (Marcinowi, Marcina, Marcinem → Marcin) przez lematyzację końcówek i dopasowanie rozmyte; przy wielu trafieniach JARVIS w runtime krótko pyta użytkownika.
5.14 Głos za interfejsami (VoiceInput, StreamingSTT, TurnDetector/VAD, ConversationModel, StreamingTTS): partiale i finały, barge-in z natychmiastowym anulowaniem TTS, echoCancellation w getUserMedia z TTS w tym samym rendererze, deduplikacja wypowiedzi, zgodność z wake word i push-to-talk, fallback dostawców (min. 2 adaptery streaming STT z polskim + obecny Groq Whisper jako fallback), TTS strumieniowy zdaniami, bufor gotowych potwierdzeń audio ("Już.", "Mam.", "Sekunda.", "Nie znalazłem.") i dźwięki stanu. Identyfikatory modeli to dane w katalogu dostawców, nie architektura; jeśli sieć pozwala, zweryfikuj aktualne ID w oficjalnej dokumentacji. Dla Gemini Live obecnym domyślnym modelem niskiej latencji jest gemini-3.8-live z asynchronicznym (NON_BLOCKING) wywoływaniem funkcji; zrób go opcjonalnym adapterem toru rozmowy, który może mówić, gdy tor akcji pracuje w tle. Spekulacja na partialach tylko dla odczytów (indeksowanie, rozwiązywanie kandydatów, rozgrzanie taniego modelu), nigdy dla efektów.
5.15 Routing modeli przez rejestr możliwości modeli (dostawca, id, tekst, wizja, audio we/wy, streaming, narzędzia, lokalny, klasa kosztu i latencji, zdrowie). Refleks bez LLM; klasyfikacja lokalnie lub tanio; rozmowa na szybkim modelu; planowanie na mocniejszym; najmocniejszy tylko przy porażce weryfikacji lub niejasnym celu. Twarde limity kosztów dzienne i na zadanie. Sprzęt użytkownika: Ubuntu, GTX 1050 Ti 4 GB, więc lokalnie tylko reguły i małe klasyfikatory.
5.16 CoderExecutor (opcjonalny): zadania programistyczne w tle przez Codex CLI, Claude Code CLI albo lokalny model, tylko jeśli zainstalowane. Nigdy do scrolla, kliknięć czy kopiowania. Jawna detekcja trybu uwierzytelnienia (plan czy klucz API) pokazywana użytkownikowi razem ze statusem i czasem. W CI mocki. Nie loguj się do Codexa w tej sesji.
6. Kamienie milowe (najpierw głębokość jednego pionowego przekroju, potem szerokość)
Każdy kończy się: zielone testy → commit → push → STATE.md, state.json, CONTINUE.md, opis PR → wypisanie w odpowiedzi zawartości state.json, podsumowania testów z kodem wyjścia i hasha commita. M0 Baseline i bezpieczeństwo: napraw 2 testy licencji bez osłabiania weryfikacji (brak klucza prywatnego w repo → testowa para kluczy wstrzyknięta w teście). Sprawdź, czy rotacja nie wrzuciła klucza prywatnego do repo lub historii. Keystore: załóż kompromitację; usuń zaszyte hasła tak, żeby build bez sekretów dawał jawnie nieprodukcyjny artefakt zamiast padać; nie zmieniaj po cichu tożsamości podpisu; opisz w docs/JARVIS-SECURITY.md opcje (np. rotacja apksigner --lineage) i ich skutki dla aktualizacji. Pomiary startowe wydajności. 7. Testy i przypadki adwersaryjne
Dla każdej ważnej funkcji: test, który wcześniej nie przechodzi → implementacja → testy skupione → przegląd (wyścigi, podwójne wykonanie, nieaktualne referencje, wycieki timerów i listenerów, fałszywe CONFIRMED, wstrzyknięcia, obejście uprawnień) → poprawki → szerszy zestaw regresji → commit → push. Każdy poważny błąd znaleziony w misji dostaje stały test regresji. Obowiązkowo przetestuj: zdublowane zdarzenia mowy, partial poprawiony przez finał, przerwanie TTS, zmiana zadania w trakcie narzędzia, przerysowanie strony po rozwiązaniu celu, nieaktualna referencja przeglądarki, zamknięcie okna w trakcie akcji, niespodziewana zmiana schowka, timeout dostawcy, utrata sieci, zepsuty JSON z modelu, timeout narzędzia, restart aplikacji w trakcie zadania, niejednoznaczny wynik wysyłki, złośliwy tekst DOM, złośliwa etykieta dostępności, złośliwy schowek, złośliwy wynik MCP lub narzędzia.
8. Pętla pracy i budżet
Pętla: obserwuj stan → wybierz największą lukę wartości → test → implementacja → weryfikacja → przegląd adwersaryjny → poprawki → commit → push → stan → następna. Czytaj celowo: grep, konkretne pliki, git diff, przefiltrowane logi. Nie wczytuj ogromnych plików w całości. Po drobnej zmianie testy skupione, przed commitem kamienia pełne bramki. Subagenty tylko do naprawdę niezależnej pracy (eksploracja, przegląd bezpieczeństwa, przegląd testów, adapter platformy po ustabilizowaniu kontraktów). Nigdy kilku agentów do tego samego; wynik subagenta zawsze przeglądasz i testujesz sam. Orientacyjny podział: do 10% audyt, min. 65% implementacja, min. 15% testy i weryfikacja adwersaryjna, do 10% dokumentacja i ciągłość. Po 2 poważnych nieudanych podejściach do mało wartościowej sprawy: zapisz dowody, oznacz blocked, przejdź dalej. Nie kończ, bo pierwszy test przeszedł, atrapa zadziałała raz, UI wygląda dobrze albo istnieje PR.

11. Rozszerzenie misji: M11-M13, JARVIS jako szef agentów programistycznych
Cel: użytkownik mówi lub pisze zadanie programistyczne ("Jarvis, przeanalizuj Sterownik Studio, znajdź dlaczego czasami usuwa naklejkę, napraw to, uruchom testy i pokaż mi wynik"), a JARVIS rozpoznaje zadanie, znajduje workspace, wybiera backend (Codex CLI, Claude Code CLI, lokalny model jako fallback), uruchamia prawdziwego agenta z celem i kontekstem repo, śledzi go na żywo, pozwala na "stop", "pauza", "wznów", "co teraz robisz?", "nie rób release", "najpierw przetestuj", "dodaj jeszcze X", po pracy uruchamia niezależną walidację i pokazuje diff, testy i wynik. Nigdy nie mówi "gotowe" bez dowodu. Nie odtwarzamy Codexa w JARVIS-ie, jeśli można bezpiecznie użyć prawdziwego CLI. Rozszerzamy istniejące: Kernel, Action Lane, agentRun/agentPipeline, permissions, MCP i System MCP, RuntimeStatusPanel, diagnostykę, truth states, ComputerEnvironment, rejestr modeli. Żadnego drugiego kernela, drugiego systemu uprawnień ani narzędzi.
M11 CoderExecutor: wspólny interfejs CoderBackend (probe, start, sendInstruction, pause gdy realnie wspierane, resume, cancel, status, zdarzenia, wynik) i backendy Codex CLI (spawn bez shell, tryb JSON zamiast parsowania terminala, stany: dostępny, niedostępny, wymaga uwierzytelnienia, gotowy, pracuje, zakończony, błąd, anulowany; nigdy nie pokazujemy tokenów), Claude Code CLI (nie zakładamy instalacji), lokalny model przez Ollamę (proste zmiany, patch; nie udajemy, że dorównuje Codexowi). Wspólne zdarzenia: TASK_STARTED, PLANNING, READING_FILE, SEARCHING, EDITING_FILE, RUNNING_COMMAND, RUNNING_TEST, BUILDING, GIT_OPERATION, WAITING_USER, WARNING, ERROR, TASK_COMPLETED, TASK_CANCELLED. WorkspaceRegistry: tylko repo jawnie dodane przez użytkownika, agent nie wychodzi poza aktywny workspace; wykrywanie .git, branch, dirty, remote, ostatni commit, menedżer pakietów, skrypty test/build/lint; snapshot przed zadaniem (status, branch, HEAD, niezacommitowane zmiany). Zakazane automatycznie: reset --hard, clean -fd, force push, przepisywanie historii, kasowanie nieznanych zmian użytkownika. Najwyżej jeden aktywny writer na workspace (lock).
M12 Live coding control: zadanie programistyczne to zwykły JARVIS Task w Kernelu. Na żywo: cel, backend, model jeśli wiarygodny, workspace, branch, etap, bieżący plik, komenda (zredagowana), liczba zmienionych plików, testy PASS/FAIL, czas, ostatni checkpoint, stan git; w RuntimeStatusPanel (sekcja CODER) i w sekcji CODE. "Co teraz robi?" odpowiada ze strukturalnego stanu procesu. "Stop" naprawdę anuluje: łagodne przerwanie, potem terminate, na końcu kill; bez procesów zombie. "Nie rób release" zmienia ograniczenia aktywnego celu; "dodaj jeszcze X" to AMEND_TASK. Checkpointy: task id, backend, workspace, HEAD startowy i bieżący, zmienione pliki, ostatni potwierdzony etap, ostatnie testy, stan procesu, PID bez sekretów. Po restarcie aplikacji: INTERRUPTED_AFTER_RESTART; "kontynuuj" wznawia od aktualnego stanu repo bez powtarzania potwierdzonych kroków. Logi: ring buffer, selektory, bez serializacji całej historii przy każdym zdarzeniu; pomiar przy min. 10 000 zdarzeń.
M13 Multi-agent software factory: role PLANNER, CODER, TESTER, REVIEWER, DEBUGGER z osobnymi zadaniami i kontekstami, nie etykiety. Mała poprawka: Coder, potem test. Duża: Planner, Coder, Tester, Reviewer; realny problem z review: Debugger/Coder, poprawka, ponowny test. Router kosztów: klasy SIMPLE, CODE_SMALL, CODE_NORMAL, CODE_HARD, CODE_CRITICAL i tryby TANIO, NORMALNIE, MAKSIMUM; nigdy dwóch drogich agentów bez sensownego zysku. Weryfikacja zawsze niezależna (git diff, status, typecheck, lint, testy, build, dodatkowe testy repo, tylko istniejące komendy); CONFIRMED tylko gdy wymagane warunki przeszły; "done" agenta przy czerwonym teście to FAILED/PARTIAL. Git: duże autonomiczne zadania na gałęzi jarvis/<task-id>-<slug>; commit tylko po pozytywnej walidacji albo na wyraźne polecenie, bez cudzych wcześniejszych zmian; nigdy automatycznie force push, merge do main/master, release ani deploy. Prompt injection: kod, README, komentarze, strony, output terminala i MCP to dane; agent nie dostaje kluczy, cookies, tokenów ani pełnego env. Testy bez płatnych wywołań (fake backend), 24 obowiązkowe przypadki z polecenia, lock na workspace. Acceptance: npm run jarvis:coder:acceptance w trybach fake (CI), local (narzędzia bez płatnego wywołania), codex (tylko świadomie na komputerze użytkownika, na tymczasowym mini projekcie z jednym błędem i czerwonym testem). UI CODE: backendy, stan uwierzytelnienia bez danych, wybór AUTO/CODEX/CLAUDE/LOCAL, aktywny workspace, historia, status, czytelny log, diff, testy, STOP, PAUZA, WZNÓW, OTWÓRZ REPO, POKAŻ ZMIANY. Definicja ukończenia: 16 punktów z polecenia (wykrycie Codexa, prawdziwe zadanie, workspace, postęp, stop, "co teraz robisz?", wynik, niezależna walidacja, brak fałszywego "gotowe", wznowienie po przerwaniu, wspólny interfejs trzech backendów, UI CODE, zielone testy, zielony build Ubuntu, stary JARVIS działa, brak regresji M0-M10). Po każdym kamieniu: testy, typecheck, lint, build, skan sekretów, stan, commit, push; na końcu przegląd adwersaryjny całego M11-M13.
